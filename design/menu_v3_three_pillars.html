设计思路

借鉴产品设计中的"三支柱"经典模型：任何业务系统的功能都可归为 "我能做什么 / 我在管什么 / 我学到什么"。

⚡

操作 Action

"我现在能做什么动作"
  • • 入库（建采购单）
  • • 出库（发货登记）
  • • 调拨（库间转移）
  • • 报损（异常登记）
  • • 盘点（盘账）
📦

资源 Resource

"我在管什么东西"
  • • 库存（在仓的货）
  • • 商品 SKU
  • • 供应商
  • • 仓库 / 库位
  • • 存储区
📊

洞察 Insight

"我从数据里学到了什么"
  • • 流水（历史轨迹）
  • • 报表（KPI 看板）
  • • 预测（销量建议）

为什么这么改

抽象的好处：4 个一级菜单（工作台 + 三支柱 + 系统）就能覆盖所有功能。未来加新菜单时，永远问"它是动作、资源、还是洞察？" — 归属自然清楚，菜单不会越来越乱。

抽象的代价：新员工第一次看到"操作 / 资源 / 洞察"会愣一下 — 这不是仓储行业的常用词。需要 10 分钟培训。

适合的公司：管理层对"信息架构"有审美追求、希望菜单结构本身能讲清产品故事。汇报时一张 3 支柱图就够了。

边界争议

三分法的难点是"边界案例"。本方案做了以下取舍：

  • 盘点 → 归"操作"（动作）。虽然它也产生"差异报告"，但本质上员工去盘点是为了"做"这个动作
  • 库存查询 → 归"资源"（看现状）。虽然它是"看"的功能，但更像在"管理这堆资源"
  • 流水 → 归"洞察"（学历史）。它是查回放、看趋势，不是查现状
