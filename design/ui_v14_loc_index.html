v14 楼栋 / 楼层 / 库位 · 三种实现方案对比

核心矛盾：「楼栋号 / 楼层 / 库位」三个维度都是物理坐标。三种实现方式各有取舍：A 重方案独立 3 张表（最严谨，但建库位要点 3 次 picker）；B 中方案把楼栋号/楼层作为库位的字段（轻量，按楼栋分组查询仍方便）；C 轻方案完全保留现状（仅 location.code 自由文本）。

你的团队 20 人，仓库不多（金山主仓 + 研发中心仓），每仓 1-2 栋楼，每栋 1-3 层，每层 5-10 个库位。本场景**通常 B 中方案够用**。看下面 3 个 mockup 自行判断。
A · 重方案 · 三级独立表
仓库数据维护
├─ 仓库
├─ 楼栋号 ← 独立菜单
├─ 楼层 ← 独立菜单
├─ 库位

建库位 = 选楼栋 → 选楼层 → 输入位号
查询 = GROUP BY 楼栋_id 一目了然
A · 重方案

三级独立表（最严谨）

3 张独立表：building(楼栋) → floor(楼层) → location(库位)，FK 串起。建库位时先选楼栋 → 选楼层 → 输入位号。能精细查询"1 号楼 3 层 总在仓量"，但每次建库位要 3 次 picker。

// RECOMMENDED
推荐 B 中方案：① 不增菜单复杂度（20 人团队菜单已经有 6 个一级，再加楼栋/楼层菜单太重）；② 建库位 1 次填齐，跟用户期待的"楼栋 + 楼层 + 库位"线性顺序一致；③ 库位列表能按楼栋分组展示，跟 A 方案查询体验差距小；④ 将来真有 5 栋楼 × 10 层规模时，可平滑升级为 A 方案（B 的 building/floor 文本字段抽出来变独立表）。
